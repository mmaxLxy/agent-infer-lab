# AgentInferLab 设计规格

日期：2026-07-15

## 1. 项目目标

构建一个面向 Agent 长上下文负载的、可复现的大模型推理性能实验项目。项目使用 vLLM 建立端到端推理基线，并通过 C++/CUDA 实现简化的分页 KV Cache 数据搬运模块，以真实测试数据说明 Agent 工作负载、推理调度、KV Cache 管理与 GPU 性能之间的关系。

项目用于形成四类可验证的秋招证据：

1. 能部署、压测和解释大模型推理服务；
2. 能使用 TTFT、TPOT、吞吐、显存和 GPU 硬件指标定位瓶颈；
3. 能独立实现、验证和优化 CUDA Kernel；
4. 能将底层优化与端到端收益区分开来，不用孤立的微基准替代系统结论。

项目不复制或公开任何内部系统、数据和实现。所有代码、负载与结果均基于公开框架和自主实验。

## 2. 范围

### 2.1 必须完成

- 可配置的 Agent 工作负载生成器；
- vLLM 推理服务基准测试；
- Transformers 或等价朴素推理基线；
- TTFT、TPOT、吞吐、P50/P99、峰值显存等指标采集；
- PyTorch 分页 KV Cache 参考实现；
- C++/CUDA 分页 KV Cache append 与 gather；
- 至少两个可比较的 CUDA 优化版本；
- 正确性、边界条件和性能回归测试；
- Nsight Systems/Compute 性能分析；
- 可复现 README、实验报告、图表和简历表述。

### 2.2 加分项

- 将自定义 CUDA 模块接入简化 Attention；
- 在接口稳定且工期允许时接入 vLLM 自定义算子路径；
- Prometheus 指标导出；
- 基于负载特征的简单参数推荐器。

### 2.3 明确不做

- 多机或跨地域推理；
- Prefill/Decode 分离；
- Kubernetes 集群调度；
- 分布式 KV Cache；
- 完整 ServingKit；
- 重写 FlashAttention；
- 未经实测的性能结论。

## 3. 使用场景与成功标准

### 3.1 工作负载

负载生成器模拟 Agent 的三项典型特征：

- 较长且可复用的 System Prompt；
- 多轮对话导致上下文持续增长；
- 请求输入、输出长度和到达间隔不均匀。

第一版实验矩阵覆盖：

- 并发数：1、8、32；
- 输入长度：512、2048、8192 token；
- 输出长度：128、512 token；
- 共享前缀比例：0%、50%、75%；
- 固定并发与泊松到达两类流量。

如果硬件不能承载某一组合，测试工具必须明确记录跳过原因，并使用可承载的最大组合完成比较，不能静默缩小输入。

### 3.2 验收标准

项目完成时应满足：

- 一条命令可运行单组基准测试；
- 一条命令可执行全部单元测试；
- CUDA 结果与 PyTorch 参考结果在声明的误差范围内一致；
- 至少完成朴素版和两个优化版 Kernel 的同环境对比；
- 每项性能数字都记录 GPU、软件版本、模型、输入 Shape、预热次数和重复次数；
- 至少输出三张图：并发与吞吐、上下文长度与 TTFT、Kernel 版本与有效带宽/延迟；
- 报告区分 Kernel 加速与端到端加速，未观察到端到端收益时如实解释原因；
- 代码仓库中不包含内部材料、内部名称、访问凭据或不可公开数据。

## 4. 系统设计

### 4.1 组件

`workloads` 负责生成确定性或随机请求序列。所有随机实验接受种子参数并保存实际请求元数据。

`backends` 提供统一推理接口，第一阶段实现 vLLM 与朴素基线。上层基准测试不依赖具体后端的调用细节。

`benchmark` 负责预热、发压、记录请求时间线和汇总指标。原始事件与聚合结果分别保存，避免只能看到最终平均值。

`metrics` 计算 TTFT、TPOT、端到端延迟、吞吐、P50/P99 和显存指标。GPU 深层指标由 Nsight 采集，不以 `nvidia-smi` 的瞬时利用率代替。

`paged_kv` 包含 PyTorch 参考实现、C++/CUDA 扩展、测试和微基准。模块只负责分页 KV 的写入与读取，不承担请求调度和完整 Attention。

`analysis` 读取结构化结果并生成图表与结论表，不把手工复制的数据作为报告来源。

### 4.2 数据流

1. 负载生成器产生带长度、共享前缀和到达时间的请求；
2. 基准测试器将请求发往选择的推理后端；
3. 后端流式返回 token 事件；
4. 指标模块从事件计算请求级与系统级指标；
5. CUDA 微基准独立运行，保存 Shape、Kernel 版本与硬件指标；
6. 分析脚本合并端到端结果和微基准结果，生成图表与报告输入。

## 5. CUDA 模块设计

### 5.1 数据模型

KV Cache 使用固定大小的物理 Block。Block Table 将每个序列的逻辑 Block 映射到物理 Block。第一版数据布局为：

`[num_blocks, block_size, num_heads, head_size]`

初始数据类型为 FP16。BF16 在 FP16 全部测试通过后增加。

### 5.2 Kernel

`append` 根据序列位置与 Block Table，将新 token 的 K/V 写入对应物理块。

`gather` 根据 Block Table，将指定序列的分页 K/V 读取到连续输出，用于正确性验证和简化 Attention 接入。

版本演进：

1. `naive`：直接索引和标量读写，作为可读基线；
2. `vectorized`：在对齐条件满足时使用向量化读写；
3. `coalesced`：调整线程与 head/head_size 映射，减少分支并改善合并访存。

架构相关的 `cp.async` 等优化只有在 Profiler 证明数据搬运是主瓶颈、目标 GPU 支持且前三个版本完成后才考虑。

### 5.3 正确性

- 与 PyTorch 参考实现逐元素比较；
- 随机生成合法与非连续 Block Table；
- 覆盖边界位置、非整 Block 长度和多个序列；
- 明确拒绝越界 Block、非法 Shape 和不支持的数据类型；
- 性能测试之前必须通过全部正确性测试。

## 6. 错误处理与可复现性

- 环境检查脚本报告操作系统、GPU、驱动、CUDA、PyTorch 和 vLLM 版本；
- 缺少 NVIDIA GPU 时，CPU 侧结构、工作负载、参考实现和单元测试仍可开发，但不生成 CUDA 性能结论；
- 模型下载失败时保存错误信息，不自动换成另一模型后继续生成不可比较结果；
- OOM 被记录为实验结果，并包含当时的配置；
- 基准测试固定预热和重复策略，保存随机种子；
- 所有生成物写入独立结果目录，源代码不依赖某次实验文件存在。

## 7. 测试策略

开发采用测试先行：

1. 为负载生成器编写确定性、长度分布和前缀复用测试；
2. 为指标计算编写人工事件时间线测试；
3. 为 PyTorch 分页 KV 实现编写映射和边界测试；
4. 使用同一组测试验证每个 CUDA 版本；
5. 增加微基准烟雾测试，防止 Kernel 无法加载或调用；
6. 端到端测试使用小模型和小负载，只验证流程，不把其结果作为正式性能结论。

性能回归不使用跨机器绝对时间作为硬阈值。相同机器上的版本比较保存原始数据，并使用中位数和离散程度判断。

## 9. 风险与降级路径

### GPU 不可用

两天内必须确认可使用的 Linux NVIDIA GPU。确认之前完成 CPU 侧框架与测试；若持续不可用，项目不能宣称完成 CUDA 性能实验，应优先协调学校服务器或合规的云 GPU。

### vLLM 环境兼容问题

将环境安装与业务代码隔离。先用官方支持的最小模型完成烟雾测试，再固定版本。不得为了跑通而连续叠加未经记录的依赖修改。

### vLLM 集成超期

自定义 CUDA 模块以独立 PyTorch Extension 交付，简化 Attention 为首选集成目标。vLLM 核心集成是加分项，不作为项目完成条件。

### 毕设算子更适合

如果毕设已有明确且更有价值的 CUDA 计算核心，用毕设算子替换分页 KV Kernel，但保留负载、基准、指标、Profiler、测试和报告框架。替换前重新确认接口与四周范围。
